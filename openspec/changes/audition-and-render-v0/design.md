## Context

The engine (`packages/engine`) realizes a manifest and seed into a bar-level trace `{ bar, beat, slot, clipHash, gain }` through `createState` / `advance` / `realize`. Its realization state is plain JSON and records the current section visit and whether the piece ended (`state.ended`, `state.bar`). The engine is zero-dependency and limited by lint to exactly specified operations (no `Math.random`, `Date`, `Intl`, transcendental `Math.*`, `**`, `TextEncoder`). It ships an ESM build plus an IIFE build that tests load into a bare `node:vm` context.

The CLI (`packages/cli`) has a hand-rolled `switch` over subcommands, with `validate` implemented as Ajv2020 then `checkManifest()` and stubs for `audition`, `bounce` and `pack`. Golden traces live in `fixtures/golden/` and are regenerated by `scripts/golden-update.mjs`.

See proposal.md for motivation and the specs for required behavior. This document covers how.

## Goals / Non-Goals

**Goals:**
- One renderer that is correct offline today and drops into an AudioWorklet later without changes: pure, block-based, with serializable state.
- Audio determinism at the same standard as the trace: sample-identical everywhere, enforced by the existing engine lint rules and golden hashes.
- A fast authoring loop: a placeholder piece and a few commands that go from an edited manifest to hearing several seeds.

**Non-Goals:**
- Real-time streaming, in which realization and rendering run interleaved. The renderer takes a complete trace. Interleaving is a player concern; the plan structure below supports adding it.
- Performance beyond "a 16-bar, 4-seed reel renders in about a second".

## Decisions

### D1. Module placement

All new audio code that must be deterministic lives in `packages/engine/src/audio/`, so the engine's lint restrictions and zero-dependency rule cover it automatically:

```
packages/engine/src/audio/
  timing.ts     barFrame(manifest, bar), constants SAMPLE_RATE = 48000, CHOKE_FRAMES = 480
  wav.ts        decodeWav(bytes) -> Stem, encodeWav16(left, right) -> Uint8Array
  render.ts     planRender(...), createRenderState(plan), renderBlock(...), renderAll(...)
  synth.ts      synthesizeClip(recipe) -> Float32Array channels (placeholder recipes)
packages/cli/src/
  args.ts       small flag parser shared by commands
  stems.ts      resolve + hash-verify stems from a directory (node:fs, node:crypto)
  commands/{validate,realize,bounce,audition}.ts
  messages.ts   Ajv error -> plain-language message table
scripts/stems-placeholder.mjs   generate .stems/, verify or --update hashes
```

- *Alternative: a separate `@spite-store/audio` package.* Rejected for now. It would need the same lint rules, tsconfig and IIFE build duplicated, and the player will want realize and render from one bundle anyway. It can be split out later without behavior changes.
- *Placeholder synthesis in the engine* is unusual for product code. It's there because the engine's lint rules are exactly the guarantee we need (exact arithmetic only), and the IIFE bundle makes the "same bytes in a bare context" test trivial. It is small and documented as a placeholder utility.

### D2. Bar timing in exact frames (determinism)

`barFrame(manifest, b)` is computed per tempo entry, not by summing bar durations:

```
N(entry)   = beats * (4 / unit) * 60 * 48000      -- an exact integer for unit in {1..64}
F(0)       = 0
F(entry_k) = barFrame at entry_k.bar, computed from entry_{k-1}
barFrame(b) = F(s) + roundHalfUp((b - s) * N / bpm)   where s = governing entry's bar
roundHalfUp(x) = Math.floor(x + 0.5)
```

`(b - s) * N` is an exact integer, so there is one correctly rounded division and one floor per bar. Error never accumulates within a tempo entry and is bounded to half a frame per tempo change. *Alternative:* summing float seconds bar by bar. Rejected because it drifts and its result depends on the summation path.

The trace is unchanged: this only maps `bar` to frames. `beat` stays 0. Meter now affects audio timing, which it did not before.

### D3. Stems: decode once, store as Float32

`decodeWav` parses RIFF chunks with `DataView` (little-endian):
- It accepts `fmt ` formats 1 (PCM: 16 or 24 bit), 3 (IEEE float: 32 bit) and 0xFFFE (WAVE_FORMAT_EXTENSIBLE) with the matching subformat. It skips unknown chunks.
- Samples are converted to `Float32Array` per channel: int16 / 32768, int24 / 8388608, and float32 as read. Every one of these is exactly representable in float32, so decoding is lossless and identical on every runtime.
- Mono is stored as one channel and read for both outputs.
- Anything else throws an error naming the problem.

Hashing is not in the engine (D9 of the first change: the engine never hashes). The CLI verifies `sha256(bytes) === hash` with `node:crypto` before decoding. The renderer receives `Map<clipHash, Stem>`.

### D4. Render plan and block rendering (determinism)

```
planRender(manifest, events, endBar, stems) -> RenderPlan
  voices: [{ slot, clipHash, gain, start, choke | null, end }]   in trace order
    start = barFrame(event.bar)
    choke = start of the same slot id's next event, or null
    end   = min(start + stemFrames, choke === null ? Infinity : choke + 480)
  totalFrames = max(barFrame(endBar), max(voice.end))

createRenderState(plan) -> { v: 1, frame: 0 }            -- plain JSON
renderBlock(plan, stems, state, n) -> { left, right, state }   Float64Array blocks
renderAll(plan, stems) = renderBlock(..., plan.totalFrames)
```

Per output frame `f`, voices are summed **in plan order** (the trace order: bar, then slot id), with a `Float64` accumulator:

```
sample = stem[ch][f - start] * gain * fade(f)
fade(f) = 1                                  if choke == null or f < choke
        = (choke + 480 - f) / 480            if choke <= f < choke + 480
        = 0 (voice ended)                    otherwise
```

Every operation is `+ - * /` on doubles in a fixed order, so the output is bit-identical across engines. Block boundaries can't change results because each frame's value depends only on `f`, not on the block it falls in. State is just the frame cursor, so it round-trips through JSON trivially.

- `endBar` comes from realization: `state.bar` after `advance(..., durationBars)`, which is the bar the piece ended at if it ended early. A small helper `realizeForRender(manifest, seed, { durationBars }) -> { events, endBar }` avoids every caller reconstructing it.
- *Alternative: voices as live state (streaming, choke discovered on the fly).* Deferred to the player change. The plan is a sorted list, so a streaming version can append voices as events arrive without changing the mixing rule.

### D5. Output encoding (determinism)

`encodeWav16(left, right)` writes a canonical 44-byte header (PCM, 2 channels, 48000 Hz, 16-bit) followed by interleaved samples. Each sample is `clamp(x, -1, 1) * 32767`, rounded with `Math.floor(v + 0.5)` (half up, as in the spec). There's no dither. The bytes are canonical, so a sha256 of the WAV file is a meaningful golden value.

### D6. Placeholder recipes and generation (determinism)

`pieces/placeholder/recipes.json` maps clip id to a recipe. Recipes use frame counts, not seconds, so there's no tempo math at synthesis time:

```jsonc
{ "kind": "clicks", "frames": 96000, "every": 24000, "accentEvery": 4, "clickFrames": 240, "level": 0.6 }
{ "kind": "tone",   "frames": 288000, "wave": "saw", "period": 109, "attack": 480, "release": 96000, "level": 0.3, "channels": 2, "detune": 1 }
{ "kind": "noise",  "frames": 48000, "seed": "hat-a", "decay": 4800, "level": 0.4, "channels": 1 }
```

- Waveforms use integer-phase arithmetic only: `phase = n % period`, so `saw = 2 * phase / period - 1`, and square and triangle are derived similarly. Envelopes are linear ramps. Noise uses the engine's Philox (`createRandom(seed).draw(['noise', n])`), which is exact by construction. No `Math.sin`. Lint enforces this because the code lives in the engine.
- Synthesis output is quantized the same way as D5, but at the stem's declared encoding (16-bit for placeholders), so the WAV bytes are canonical.
- `scripts/stems-placeholder.mjs` imports the built engine, synthesizes every recipe, hashes with `node:crypto`, and writes `.stems/<hex>.wav`. It verifies or, with `--update`, rewrites `manifest.json` hashes (preserving key order and formatting via `JSON.stringify(..., 2)`). The root script is `"stems:placeholder": "pnpm --filter @spite-store/engine build && node scripts/stems-placeholder.mjs"`.
- Placeholder content: a counting `clicks` clip (beat clicks with an accent on beat 1), a `tone` pad with a long release tail (at least one bar past its body), a short `noise` hat, a `tone` bass, and an exclusion pair. Tempo is 120 bpm 4/4, changing to 3/4 at bar 8, so meter math is exercised.

Noise draws use recipe-seeded paths that are entirely separate from realization. No realization decision path or `TRACE_FORMAT` changes.

### D7. Golden audio

`fixtures/golden/placeholder.audio.<seed>.json` holds `{ manifest, seed, durationBars: 16, renderFormat: 1, frames, wavSha256, barSha256: [...] }`. `barSha256[b]` hashes the encoded 16-bit samples for frames `[barFrame(b), barFrame(b+1))`, and one extra entry covers the tail after the last bar. This is small enough to commit, and on drift it locates the first differing bar.

- Tests and `pnpm golden:update` synthesize stems **in memory** from the recipes, so the golden test never depends on `.stems/` existing.
- `RENDER_FORMAT` (exported from the engine) follows the same bump policy as `TRACE_FORMAT`: any change that alters samples for an existing (manifest, seed, stems) bumps it, and changes ship with `golden:update`.

### D8. CLI commands

- `args.ts` is a small parser for `--flag value`, repeatable `--seed` and boolean `--no-play`/`--json`. It rejects unknown flags with usage (exit 2). There's still no CLI framework.
- Section info for `realize` and the audition summaries comes from stepping `advance` one bar at a time and reading `state.visit`. This is cheap at authoring sizes, and it keeps section reporting out of the trace format.
- `audition` renders each seed independently with `renderAll`, concatenates the renders with 96,000 frames of silence, encodes once, and writes to `--out` or `os.tmpdir()/spite-audition-<manifestId>-<hash8>.wav`. It plays with `spawn('afplay', [path], { stdio: 'inherit' })` only when `process.platform === 'darwin'` and not `--no-play`, and exits with afplay's status. Tests always use `--no-play`.
- `bounce` and `audition` resolve stems for only the clips that the planned voices use (the spec's "every clip the render needs"), so a partial stems directory works for pieces that never reach some clips.

### D9. Plain-language validation messages

`messages.ts` maps an Ajv error to a message using `schemaPath` and `keyword`, with the instance value read from the parsed manifest at `instancePath`:

| Ajv error | Message |
|---|---|
| `#/$defs/id/pattern` | `"Drums Loop" is not a valid id: use 1-64 lowercase letters, digits, "-" or "_", starting with a letter or digit` |
| hash `pattern` | `"sha256:ABC" is not a valid hash: expected "sha256:" followed by 64 lowercase hex characters` |
| `specVersion` `const` | `unsupported specVersion "9.9": this tool supports "0.1"` |
| `required` | `missing required property "title"` |
| `additionalProperties` | `unknown property "foo"` |
| `type`, `minimum`, `maximum`, `exclusiveMinimum`, `minItems`, `enum` | `expected <type/limit/allowed values>, got <value>` |

Any unmapped keyword falls back to Ajv's message prefixed with `invalid value`, but the test suite asserts that no message from the shipped examples contains a raw regular expression.

## Risks / Trade-offs

- [Choke is keyed by slot id, so two sections reusing a slot id for unrelated material will choke each other] → This is intended ("slot id = voice") and matches how history and no-repeat already work. Documented in the engine README.
- [Exclusions no longer guarantee audible separation, because tails can overlap an excluded clip] → Stated explicitly in the spec. A future per-clip tail policy can tighten it.
- [Synthesis code in the engine package grows its public surface] → It is exported under a clearly named placeholder API and covered by the same zero-dependency and lint rules. It can move out when real stems replace placeholders.
- [Large stems held fully in memory] → Fine for authoring sizes. Streaming decode is a player concern.
- [`afplay` is macOS-only] → `--no-play` and printing the path work everywhere. A cross-platform player is out of scope.
- [Ajv message mapping relies on `schemaPath` strings that change if the schema is restructured] → Tests over all invalid examples catch regressions, and the fallback still produces a message.

## Migration Plan

Additive. Existing trace goldens, `TRACE_FORMAT` and the manifest schema are unchanged. The CLI stubs for `audition` and `bounce` become real commands, and `pack` stays a stub. `.stems/` is added to `.gitignore`.
